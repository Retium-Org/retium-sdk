# RCP-1: the Retium contract standard

RCP-1 is the agreement between a contract and everything that looks at it — the chain, wallets, explorers and other contracts. It answers three questions:

1. **Which contract is this?** — identity
2. **What does it claim to be?** — metadata
3. **How much does calling it cost?** — weight

It is deliberately small. There is no inheritance, no proxy pattern and no upgrade mechanism to learn.

## 1. Identity: a contract is its code

A contract id is not handed out by the chain. It is derived:

```
contract_id = hex(blake3( wasm ‖ deployer ‖ [weight] ‖ name? ‖ symbol? ‖ rcp_type? ‖ traits… ))
```

Consequences worth understanding before you deploy:

* **You can compute the id first.** The SDK does: `retium deploy … --dry-run`, or `retium_sdk::contract::contract_id(...)`. The transaction you sign names that id.
* **The same code from a different account is a different contract.** So is the same code with different metadata.
* **Deploying the same thing twice is refused.** The id already exists.
* **Code never changes.** There is no upgrade. A "new version" is a new deployment with a new id, and you move your users to it deliberately.

Alongside the id the chain records a **code hash**: `blake3(wasm)`, computed by the node, not declared by you. That is what lets anyone check that a deployed contract is the source you published — see [Verifying code](06-verifying-code.md).

## 2. Metadata: what the contract claims to be

Metadata is embedded in the wasm as a marker, JSON, and a zero byte:

```
RCP_METADATA:{"rcp_type":"counter","traits":["demo"],"capabilities":["execute"],"weight":1,"version":"v1.0.0"}\0
```

The simplest way to place it is a static byte string your contract keeps:

```rust
#[used]
#[no_mangle]
static RCP_METADATA_BLOB: &[u8] =
    b"RCP_METADATA:{\"rcp_type\":\"counter\",\"traits\":[\"demo\"],\"capabilities\":[\"execute\"],\"weight\":1,\"version\":\"v1.0.0\"}\0";
```

| Field | Meaning | Checked by the chain |
|---|---|---|
| `rcp_type` | What kind of contract this is (`token`, `vault`, `counter`…) | must not be empty |
| `traits` | Free-form markers other tools read | at least one trait or capability |
| `capabilities` | What the contract can do | at least one trait or capability |
| `weight` | Gas weight 1–5 | must be 1–5 **and** match the chain's own analysis of your code |
| `version` | Your version string | must not be empty |

A contract without metadata still deploys — the chain records a minimal placeholder — but nothing can tell what it is. Declare it.

### Read this part twice

**Metadata is a claim by whoever deployed the contract, not a fact the chain checks.** Anyone can deploy a contract whose `name` and `symbol` match a well-known token and declare any traits they like. The only thing the chain computes is the code hash.

So:

* identify contracts by **id** or **code hash**, never by name or symbol;
* if you build a wallet or explorer, show the id, and never let a symbol alone decide what a user is approving;
* `supports_capability` tells you what another contract *claims*. Treat it as a hint, never as permission.

## 3. Weight: what a call costs

Weight sets the flat gas fee for calling your contract:

| Weight | Fee | Typical |
|---|---|---|
| 1 | $0.01 | reads, transfers, simple state changes |
| 2 | $0.05 | mint, burn |
| 3–4 | $0.10–$0.25 | heavier logic |
| 5 | $0.50 | deploy; heavy contracts |

Weight is not a free dial. At deploy the chain analyses your code and refuses the deployment if your declared weight is far from what the code looks like. Declare honestly: too low and the deploy fails, too high and your users pay more than they need to.

Some standard method names are always charged at a fixed weight regardless of your declaration — `transfer`, `balance_of`, `approve`, `name`, `symbol`, `decimals`, `total_supply` are weight 1, and `mint` and `burn` are weight 2. Naming your methods the standard way keeps your users' costs predictable.

## 4. Conventions worth following

RCP-1 does not force an interface on you, but tooling assumes the usual names. If you build a fungible token, implementing `transfer`, `balance_of`, `total_supply`, `name`, `symbol` and `decimals` means wallets can show it without special-casing your contract.

Two practices that separate a serious contract from a risky one:

* **Do not hardcode an owner address.** Record the first caller in `init`, as the example does. Hardcoding means anyone who deploys your published code hands control to you, which is almost never what either of you wants.
* **Say what the owner can do,** and if the owner can mint without limit, say that too. If ownership is meant to end, provide a way to renounce it and use it.
