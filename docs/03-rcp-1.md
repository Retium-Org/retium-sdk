# RCP-1, the Retium contract standard

RCP-1 is the agreement between a contract and everything that looks at it, meaning the chain, wallets, explorers and other contracts. It answers three questions.

1. **Which contract is this?** Identity.
2. **What does it claim to be?** Metadata.
3. **How much does calling it cost?** Weight.

It is deliberately small. There is no inheritance and no proxy pattern to learn.

## 1. Identity. A contract is its code

A contract id is not handed out by the chain. It is derived.

```
contract_id = hex(blake3( wasm + deployer + [weight] + name? + symbol? + rcp_type? + traits... ))
```

`weight` is always 5 for a deploy, and the optional parts come from the deploy request's metadata, in that order, only when present. Some things follow from this.

* **You can compute the id first.** `retium deploy ... --dry-run` prints it, and so does `retium_sdk::contract::contract_id(...)`. The transaction you sign names that id.
* **The same code from a different account is a different contract.** So is the same code with different metadata.
* **Deploying the same thing twice is refused,** because the id already exists.
* **Code never changes.** A new version is a new deployment with a new id, and you move your users to it deliberately.

Alongside the id the chain records a **code hash**, `blake3(wasm)`. The node computes it, so the deployer cannot declare it. That is what lets anyone check that a deployed contract is the source you published. See [Verifying code](06-verifying-code.md).

## 2. Metadata. What the contract claims to be

Metadata is embedded in the wasm as a marker, JSON and a zero byte. The contract crate writes it for you.

```rust
retium_contract::rcp_metadata!(
    r#"{"rcp_type":"counter","traits":["demo"],"capabilities":["execute"],"lockable_fields":[],"evolves_from":"","weight":5,"version":"v1.0.0"}"#
);
```

All seven fields are required. A missing field makes the chain refuse the deploy, so write empty values where you have nothing to say.

| Field | Meaning | Checked by the chain |
|---|---|---|
| `rcp_type` | what kind of contract this is (`token`, `vault`, `counter` and so on) | not empty |
| `traits` | markers other tools read, such as `fungible` | at least one trait or capability |
| `capabilities` | what the contract can do | at least one trait or capability |
| `lockable_fields` | fields the contract promises never to change once set | |
| `evolves_from` | the id of the contract this one replaces, or `""` | the parent must exist |
| `weight` | gas weight 1 to 5 | must fit the chain's analysis of the code |
| `version` | your version string, such as `v1.0.0` | not empty |

A contract without metadata still deploys, and the chain records a minimal `Unknown` placeholder, but nothing can tell what it is. Declare it.

### Deploy metadata

The deploy request can also carry a `metadata` object. Its fields go into the contract id and override the embedded record.

| Deploy field | Effect |
|---|---|
| `name` | replaces `rcp_type`, and is what wallets show as the name |
| `symbol` | added as a `symbol:` trait |
| `decimals` | added as a `decimals:` trait, 0 to 38 |
| `traits`, `capabilities`, `weight`, `version` | replace the embedded values |

The names RTM, RTD and Retium Dollar are reserved for the chain's own coins and are refused, including look-alike spellings. So are invisible or text-direction characters in any name, trait or version. The public endpoint refuses deploy metadata over 8 KiB. `retium deploy --dry-run` shows the record that results.

### Read this part twice

**Metadata is a claim by whoever deployed the contract, not a fact the chain checks.** Anyone can deploy a contract whose `name` and `symbol` match a well-known token and declare any traits they like. The only thing the chain computes is the code hash.

So identify contracts by **id** or **code hash**, never by name or symbol. If you build a wallet or explorer, show the id, and never let a symbol alone decide what a user is approving. `supports_capability` tells you what another contract *claims*, so treat it as a hint, never as permission.

The same goes for `evolves_from`. It links a new contract to the one it replaces, but treat the link as a claim and check that both contracts have the same deployer before you follow it.

## 3. Weight. What a call costs

Weight sets the flat gas fee for calling your contract.

| Weight | Fee | Typical |
|---|---|---|
| 1 | $0.01 | transfers, simple state changes |
| 2 | $0.05 | `mint`, `burn` |
| 3 | $0.10 | standard contracts |
| 4 | $0.25 | complex contracts |
| 5 | $0.50 | deploys, heavy contracts |

Weight is not a free dial. At deploy the chain scores your code by its instructions, loops, calls and memory operations, and the declared weight must be that score or one above it. Almost any contract written in Rust scores 5, so declare 5. `retium deploy --dry-run` shows the score before you send anything.

Some method names are always charged at a fixed weight, whatever you declare. `transfer`, `transfer_from`, `approve`, `allowance`, `balance_of`, `name`, `symbol`, `decimals` and `total_supply` are weight 1, and `mint` and `burn` are weight 2. Every other method is charged at the contract's declared weight.

## 4. Conventions worth following

RCP-1 does not force an interface on you, but tools assume the usual names. If you build a fungible token, follow [Tokens](09-tokens.md) so wallets can show it without special handling.

Two practices separate a serious contract from a risky one.

* **Do not hardcode an owner address.** Record the first caller in `init`, as the example does. Hardcoding means anyone who deploys your published code hands control to you, which is almost never what either of you wants.
* **Say what the owner can do,** and if the owner can mint without limit, say that too. If ownership is meant to end, provide a way to renounce it and use it.
